# Configure the network

Once an account's CloudFormation stack has run, SleakOps needs to know which VPC, subnets and gateways to use before it can deploy a cluster into it. This step maps that existing AWS network to the inputs SleakOps requires.

## Find accounts waiting on network configuration

If you have accounts still waiting on network configuration, you'll see an alert for it on the Providers list. The banner reads **Network configuration pending** and names the provider with pending accounts. Its **Configure networking** button takes you straight to that account's network configuration form in **Accounts & Networking**. Only admins see this alert.

## Select the VPC

The account's detail panel opens on a single required field: **VPC**. The dropdown lists every VPC SleakOps discovered in the account, as `<name or id> · <cidr_block>`.

<Zoom overlayBgColorEnd="rgba(255, 255, 255, 0.8)">
  <img
    src={require("./network-configuration/network-config-vpc.png").default}
    alt="Network configuration form with the VPC dropdown not yet selected"

</Zoom>

SleakOps discovers the account's whole network topology once, when the form opens (**Discovering network topology…**). Selecting a VPC then narrows the subnets, NAT Gateways and Internet Gateways shown below to the ones in that VPC.

## Assign subnets to slots

| **Setting**         | **Description**                                             |
| -------------------- | ------------------------------------------------------------- |
| **Public subnets**     | Subnets with a route to the Internet Gateway.                |
| **Private subnets**    | Subnets that reach the internet through a NAT Gateway.        |
| **Persistent subnets** | Subnets for stateful resources (databases, storage).          |

All three slots are required — each needs at least one subnet. The descriptions above are guidance: SleakOps doesn't check the subnets' routes. The same subnet can be assigned to more than one slot.

## Gateways

- **NAT Gateway(s)** — select at least one. If the VPC has no NAT Gateway at all, SleakOps shows **This VPC has no NAT Gateways**.
- **Internet Gateway** — a single required dropdown. If the VPC has none, SleakOps shows **This VPC has no Internet Gateway attached**.

Each NAT Gateway's Elastic IP is taken automatically from AWS — there's no field to pick it separately. A NAT Gateway without one is flagged with **This NAT Gateway has no Elastic IP attached**.

## Submit and import

**Save and apply** stays disabled until all three subnet slots, at least one NAT Gateway with an Elastic IP, and the Internet Gateway are set. Once you submit, the account moves to **Creating…** while SleakOps applies the configuration — the panel switches to the **network explorer** automatically when it finishes.

The network explorer is a read-only view of the imported network: the VPC, its route tables, the Internet Edge (Internet Gateway, NAT Gateway and its Elastic IP), and the subnets grouped by Public, Private and Persistent.

## Protect your public load balancer with a web application firewall

SleakOps can put AWS WAF in front of each cluster's public load balancer, so malicious traffic is stopped before it reaches your applications. The firewall uses AWS managed rules for IP reputation, known bad inputs and the core rule set. It is off by default.

It applies to clusters created by SleakOps (not imported clusters) and only to the public load balancer.

### Turn it on

Only admins can change it.

1. Open **Accounts & Networking** and select the account.
2. Open **Web application firewall**.
3. Enable the firewall for the cluster you want to protect.

The firewall starts in **Count** mode: requests are only counted and nothing is blocked. Review the matches for about a week, then switch the cluster to **Block**.

### Review false positives

Check what the rules match before you block:

- In your AWS account, open the **AWS WAF** console, select the web ACL `sleakops-<cluster>` and review the metrics per rule and the sampled requests.
- If you enabled logging, full logs are in the CloudWatch Logs group `aws-waf-logs-<cluster>`, kept for 30 days. The `Authorization` and `Cookie` headers are hidden.

A blocked request gets a `403` from the load balancer. If a specific rule blocks legitimate traffic, keep that rule in **Count** from the same form while the others keep blocking. Request bodies larger than 8 KB are never blocked by the body size rule.

### Optional rule groups

You can add more AWS managed rule groups, all off by default: anonymous IPs, SQL injection and Linux.

### Cost

AWS bills the firewall in your account, not SleakOps. Reference prices for us-east-1:

- USD 5 per month per web ACL.
- USD 1 per month per rule group (USD 8 per month in total with the default rule groups).
- USD 0.60 per million requests.

Logging adds CloudWatch Logs charges. Prices vary by region: see [AWS WAF pricing](https://aws.amazon.com/waf/pricing/).

### Limits

- A load balancer can have only one web ACL. If your public load balancer already has a web ACL you attached yourself, SleakOps does not replace it and does not enable the firewall.
- If one of your own Ingresses in the same ingress group sets an AWS WAF annotation, yours wins or the load balancer stops updating. Remove that annotation before you enable the firewall.
- If the load balancer can't reach AWS WAF, AWS does not forward the request to your application (AWS default behavior), even in **Count** mode.

### Turn it off

Disabling the firewall removes the web ACL. Deleting the cluster removes it too.
